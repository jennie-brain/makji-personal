# MAKJI STOCK 기획안 AZTKS 종합 평가표

## 📊 종합 평가 요약 (AZTKS Rubric)

전달해주신 다양한 소스(기획안 MD/Notion, PPT 발표덱, 거의최종프로토타입.html, 자사몰, 외부 데이터)를 기반으로 기획안을 '알잘딱깔센(AZTKS)' 기준에 따라 종합 평가했습니다. 

전반적으로 외부 데이터(환율, 검색 트렌드)를 이커머스(베이커리) 도메인에 접목하여 **매일 방문해야 할 이유를 만들어내는 기획의 완성도가 매우 뛰어납니다.**

---

### A: 알아서 (Aware) - 의도 파악과 문제 해결력 [★★★★★]
- **고객과 기업의 니즈 정확히 파악**: 기업 RFP에서 요구하는 '상품 관심 및 재방문 유도'라는 과제를 '오늘의 빵값(주식 시장 컨셉)'으로 완벽하게 풀어냈습니다. 할인을 단순한 이벤트가 아닌 '가치 탐색'의 경험으로 치환한 점이 훌륭합니다.
- **실질적 데이터 활용**: 단순히 그럴듯한 컨셉에 머물지 않고, 네이버 검색 데이터랩(관심도)과 수출입은행 환율 데이터(거시경제)를 변수로 사용하여 명확한 할인 산식을 도출해 낸 점이 돋보입니다.

### Z: 잘 (Zenith) - 논리와 디테일의 완성도 [★★★★☆]
- **정교한 가격 가드레일**: 환율 하락 시 최대 28%p, 검색 추가 할인 10%p를 합산해 최대 38%p의 하드캡(Hard-cap)을 설정한 부분은 재무적 안정성까지 고려한 최상의 디테일입니다. 백테스트 결과(중앙 할인율 12.0%p)까지 문서화하여 기획의 신뢰성을 높였습니다.
- **프로토타입 구현도**: `거의최종프로토타입.html` 확인 결과, Pretendard 폰트를 활용하고 주식 시장의 UI를 모바일 우선(Mobile-First)으로 깔끔하게 차용한 점이 눈에 띕니다. (단, 실제 연동 시 서버 부담이나 API Rate Limit에 대한 방어 로직 디테일은 추후 보완이 필요할 수 있습니다.)

### T: 딱 떨어지게 (Tightly) - 스코프와 실현 가능성 [★★★★★]
- **MVP와 확장의 명확한 분리**: 당장 구현해야 할 기능(Bread Market, 빵시세 비교, 구매 전환)과 추후 확장할 기능(Bakery ETF, FX Bakery, Bread Index)을 명확하게 나누어 프로젝트의 실현 가능성을 대폭 끌어올렸습니다.
- **명확한 성과 지표(KPI)**: MAKJI STOCK 익일 재방문율, 자사몰 구매 이동률 등 측정 가능한 지표를 구체적으로 나열하여 기획의 타당성을 입증했습니다.

### K: 깔끔하게 (Klean) - 구조와 전달력 [★★★★★]
- **문서화 및 발표(PPT) 구성**: 기획안(v2.md)의 목차 구성, RFP 요구사항 대응표, 상세 산식까지 군더더기 없이 깔끔하게 정리되어 있습니다. 개발자, 디자이너, 클라이언트(B2B) 모두가 이해하기 쉬운 완벽한 구조입니다. 
- **사용자 여정(User Journey)**: '오늘 빵값 확인 -> 예측 참여 -> 익일 재방문 및 쿠폰 수령'으로 이어지는 흐름이 매우 자연스럽고 직관적입니다.

### S: 센스있게 (Sensible) - 차별화 포인트와 매력도 [★★★★★]
- **참여형 게이미피케이션**: 단순히 빵값을 보여주는 것에 그치지 않고, '내일 가격 예측(오른다/내린다)' 기능을 넣어 사용자의 능동적인 참여를 유도한 점은 압도적인 센스입니다.
- **마케팅 소구점(Copywriting)**: "매일 오전 9시, 오늘의 빵값이 열립니다"와 같은 카피는 소비자 언어를 정확히 구사하여 광고(Meta 등) 소재로 활용하기에 최적화되어 있습니다.

## 💡 최우선 개선 제안 (우선순위 도출)

현재 기획은 매우 훌륭하며 MVP 런칭에 무리가 없습니다. 다만 실제 라이브를 위해 다음 3가지를 보완하는 것을 추천합니다.

1. **환율 변동성 정체 시 방어 로직 마련 (S - 센스 보완)**
   - 평일 기준 환율이 오르거나 동결될 경우 환율 할인이 0%가 됩니다. 장기 박스권 횡보 시 '빵값의 변동이 없는 날'이 지속되면 서비스의 핵심 가치(매일 바뀌는 빵값)가 퇴색될 수 있습니다. 
   - **대안**: 환율 할인이 0%일 때만 발동하는 '서프라이즈 랜덤 지수'나 '우천/날씨 할인' 같은 3순위 변수를 백업으로 두는 것을 고려해 보세요.
2. **트래픽 집중(스파이크) 대비 (Z - 디테일 보완)**
   - '매일 오전 9시 가격 공개'라는 메시지는 9시 정각에 트래픽을 집중시킵니다. 
   - **대안**: 9시에 가격 계산 로직을 실시간으로 돌리기보다, 8시 50분에 백그라운드 스케줄러로 가격을 미리 계산해 DB나 캐시(Redis 등)에 올려두고 9시에는 캐시 데이터만 뿌려주는 정적 화면 위주로 프로토타입/서버 구조를 설계해야 합니다.
3. **사용자 로그인/세션 유지 방식 확정 (T - 실현가능성 보완)**
   - 기획안 내 '브라우저 익명번호 vs 참여번호' 중 택1을 해야 합니다. 익명번호(Local Storage 기반)가 진입 장벽이 낮아 이탈률을 줄일 수 있으므로 **익명번호 기반(Cookie/Local Storage)을 MVP의 기본값으로 채택**하는 것을 적극 권장합니다.
