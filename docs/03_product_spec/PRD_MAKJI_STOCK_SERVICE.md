## 1. 제품 개요

MAKJI STOCK은 **검색트렌드**와 **환율**을 반영해 하루 두 번(오전장·오후장) 달라지는 빵값을 보여주는 서비스다. 사용자는 MAKJI STOCK에서 오늘 빵값을 확인하고, 구매할 상품을 선택하면 막지 자사몰(`makji.kr`, 카페24)로 이동한다. 두 사이트는 별도로 운영하며, 실제 주문·결제는 자사몰에서만 진행한다.

| 항목 | 내용 |
| --- | --- |
| 서비스명 | MAKJI STOCK |
| 타깃 사용자 | 매일 달라지는 빵 시세와 혜택을 확인하며, 단순 구매를 넘어 새로운 구매 경험을 즐기는 온라인 베이커리 소비자 |
| 핵심 가치 | 하루 두 번 바뀌는 가격을 확인하고 원하는 빵의 구매 시점을 판단하는 경험 |
| 핵심 메시지 | 매일 다시 매깁니다 — 빵값이 주식처럼 움직여요 |
| 대표 체감 수치 | 4,500원 빵 기준 하루 평균 약 217원 변동(91일 백테스트, **舊 단일갱신 모델 기준 잠정치 — 10장 참고**. 화면에 산식·근거로 노출하지 않음) |

**핵심 이용 경험:** 오늘 빵값 확인(오전장·오후장) → 상품 비교 → 막지 자사몰에서 구매<br>
**추가 참여 경험:** 오전 가격 잠금(하루 1회, 빵 1개) → 오늘의 보상 고르기(안정형/공격형, 정확한 % 범위 미확정 — 22장) → 가격 하락·지정가 이메일 알림

> **MVP 상품 수 미확정:** 이 PRD는 계속 "MVP 5종"으로 서술하되, `makji-personal/docs/기획-정리-2026-09-23-할인상한과-상품옵션.md`는 냉동생지를 포함한 6종으로 범위가 넓어졌다고 기록한다. 최종 상품 수는 기업 확인 후 확정한다(22장).

가격 할인 자체가 목적이 아니라, 오늘의 가격을 확인하는 행동이 상품 탐색과 재방문으로 이어지게 하는 것이 핵심이다. 개인의 검색 한 번이 즉시 할인으로 바뀌는 구조가 아니며, 확정된 환율 데이터와 상품별 검색 관심도를 정해진 산식으로 반영한다.

## 2. 배경과 문제 정의

**기업 RFP 요구:** 외부 시장 데이터를 식품 구매 경험에 연결해 상품 관심·재방문·구매 전환을 유도하고, 메타 광고용 이벤트 페이지·SNS 홍보 소재로 신규 고객을 자사몰 구매로 연결한다.

**현재의 한계**

- 고정된 가격과 상품 진열은 다음 날 다시 확인할 새로운 정보가 적다.
- 광고 유입 이후 둘러볼 콘텐츠와 재방문 장치가 부족하다.
- 가격 확인과 실제 구매가 서로 다른 서비스에서 진행되므로 이동 맥락을 명확히 알려야 한다.

**기회:** "오늘 빵값은 얼마지?"라는 질문으로 가격 확인의 재미를 만들고, 이를 다음 방문과 구매 기회로 전환한다.

1. **아침 시세 확인:** "오늘 막지빵은 얼마일까?"라는 궁금증으로 접속
2. **오늘 가격 공개:** 오전 9시에 오늘 가격, 어제 대비 변동액, 가격이 달라진 이유를 확인
3. **재방문 습관:** 오늘과 내일의 가격을 비교하거나 예측 결과·알림을 확인하기 위해 다시 방문

SNS·광고 카피(소비자 언어, 산식 언급 금지): "오늘 막지빵, 어제보다 얼마나 달라졌을까요?" / "매일 오전 9시, 오늘의 빵값이 열립니다."

## 4. 목표(Goals)와 비목표(Non-goals)

### Goals

1. 방문 즉시 오늘 가격과 정가 대비 할인율을 이해하게 한다.
2. MVP 5종의 가격 흐름을 비교하고 상품 상세로 이동하게 한다.
3. 환율 할인과 검색수요 할인을 소비자 언어로 설명한다(산식·데이터 출처는 노출하지 않는다).
4. 선택 상품과 최종가격을 유지한 채 `makji.kr` 구매 페이지로 연결한다.
5. 내일 가격 예측과 가격 하락·지정가 알림으로 재방문을 습관화한다.

### Non-goals

- MAKJI STOCK 안에서 주문·결제를 처리하지 않는다.
- 로그인·회원가입 기능을 두지 않는다(7-3, 13장 참조).
- 운영 대시보드나 가격 산식·경보 기준을 소비자 화면에 노출하지 않는다.
- 구매 전환, 재방문 효과, 최적 할인율, 상품 수익성이 이미 검증되었다고 주장하지 않는다.
- '대란', '완판 행진' 같은 상한 돌파형 프레이밍을 사용하지 않는다(정찰제·투명성 원칙과 충돌).
- 38%p 상한을 넘는 이벤트성 할인은 만들지 않는다(23장).

## 5. 대상 사용자와 핵심 시나리오

주 사용자는 건강한 빵과 가격 혜택에 관심이 있고, 인스타그램·카카오톡 등 모바일 채널에서 막지를 처음 접하거나 재방문하는 소비자다. "오늘은 어떤 빵이 얼마나 내려갔을까?"를 빠르게 확인하고 구매 시점을 판단하려 한다.

## 10. 가격 정책(舊 단일갱신 모델 — 3구간 모델로 전환 중, 22장 참고)

> 아래 산식·백테스트는 "매일 09:00 1회 갱신" 모델 기준이다. 9장에서 설명한 오전장·오후장 3구간 모델로 전환하면서 환율 비교 기준 시점 자체가 바뀌므로(D-2/D-1 비교 → 전일 종가/당일 시가 비교), 이 산식은 **구조 참고용으로만 유지**하고 실제 배포 산식은 새 모델 기준으로 재도출해야 한다. 시장 할인 상한 자체도 38%p 단일 캡에서 "시장 20%p + 보상 최대 18%p" 분리안으로 바뀔 수 있다(`기획-정리-2026-09-23-할인상한과-상품옵션.md` 2.4절, 미확정).

```text
환율 하락률 = (D-2 확정 환율 − D-1 확정 환율) ÷ D-2 확정 환율 × 100   (0 이하이면 0)
원시 환율할인 = max(0, 환율 하락률 × 0.28 × 50)
환율할인 = min(28%p, 원시 환율할인)
검색수요 추가 할인 = min(10%p, 네이버 검색지수(0~100) × 0.1)   // 자동 반영, 별도 쿠폰 없음
캡 적용 전 원시 할인율 = 원시 환율할인 + 검색수요 추가 할인
총할인율 = min(38%p, 환율할인 + 검색수요 추가 할인)
오늘 가격 = 정가 × (1 − 총할인율 ÷ 100)
```

**원칙**

1. 환율이 하락한 경우에만 환율할인을 적용한다(상승·동일 시 0%p).
2. 전일 가격에 누적하지 않고 매일 정가에서 다시 계산한다.
3. 표시가격과 자사몰 실제 결제가격은 일치해야 한다(원 단위 처리 규칙은 자사몰 연동 정책에 맞춰 확정).
4. 외환시장 비영업일에는 마지막 영업일에 계산된 환율 하락률을 그대로 이월하되, 검색지수는 비영업일에도 갱신되므로 최종 가격은 달라질 수 있다.

**91일(2026.06.12~09.10, 달력 일수 기준) 백테스트 결과(舊 모델 기준, 잠정치):** 중앙 할인율 12.0%p, 평균 12.5%p, 최대 30.9%p, 38%p 상한 도달 0일. 4,500원 기준 평균 할인금액 약 563원, 평균 일별 변동폭 약 217원(서로 다른 개념이므로 화면에서 구분 표시). 변동성 기여도는 환율 97%, 검색 3%. 이 결과는 산식의 동작 특성을 보여줄 뿐 구매 전환·재방문 효과·수익성을 증명하지 않는다.

> **재검증 필요:** 비교 기준을 "전일 종가 → 당일 시가"(오버나이트 갭)로 바꿔 다시 계산하면 이 백테스트 결과와 달라질 수 있다는 내부 검토가 있었다(6년 구간에서 28%p 캡이 0회 발동한다는 별도 분석). 舊 모델 수치를 새 산식·새 결과 없이 그대로 제안서 등에 재사용하지 말 것.

**총혜택 예산(원 단위 캡) 전환 — 미확정:** `기획-정리-2026-09-23-할인상한과-상품옵션.md`는 세트·옵션 상품까지 고려해 "정상가 대비 38%"를 %p 산식이 아니라 **원 단위 예산**(`최종결제가 ≥ 비교기준금액 × 0.62`)으로 재정의하고, 잠금·보상 쿠폰을 구매 직전 시점의 실제 판매가 기준으로 재계산해 발급하는 방식을 기본 정책으로 제안한다. 이 PRD는 이 방향을 유력한 차기 산식으로 기록만 하고, 확정 전까지 위 舊 산식을 그대로 둔다.

상세 계산식·계산 예시는 `9_14_기획안_v2.md` 부록 B(舊 모델) 및 `makji-personal/docs/기획-정리-2026-09-23-할인상한과-상품옵션.md`(신 모델 제안)를 참조한다.

## 11. 가격 가드레일과 경보 체계

**기록 항목:** 원시 환율할인, 캡 적용 전 원시 할인율, 최종 할인율, 상한 초과폭(`max(0, 캡 적용 전 원시 할인율 − 38%p)`), 상한 도달일, 상한 적용 상품일 비율(최근 7일 상한 도달 상품일 수 ÷ 전체 상품일 수 × 100).

| 단계 | 조건 | 시스템 처리 | 담당자 조치 |
| --- | --- | --- | --- |
| 정상 | 최근 7일 상한 도달 0일이고 상한 적용 상품일 비율 5% 미만 | 정상 적용 | 정기 모니터링 |

| 경고 | 최근 7일 상한 도달 2일 이상, 2일 연속 도달, 상품일 비율 10% 이상, 상한 초과폭 5%p 이상 또는 하루 5종 중 3종 이상 도달 | 운영·재무 담당자에게 경고 | 데이터 오류 확인 후 환율 승수·검색수요 할인 산식 검토 |

> **재검토 필요:** 하루 가격 갱신이 1회에서 2회(오전장·오후장)로 늘고, 10장의 "총혜택 예산" 안이 채택되면 이 표의 판정 단위("상품일")와 캡 기준(%p → 원 단위)도 함께 바뀌어야 한다.

| 할인 표시의 법적 위험 | 정가 대비 할인율과 할인가를 매일 다시 계산해 표시하는 방식은 표시·광고 관련 법규 검토가 필요하다 | 기준가격·할인 구성·적용일·데이터 기준을 화면에 명시하고 법무 검토. 소비자가 구매 전에 가격과 거래조건을 이해할 수 있도록 고지 |
| 가격 모델 전환 재검증 | 단일갱신(D-2/D-1) → 3구간(전일종가/당일시가) 모델 전환으로 10장 백테스트·11장 가드레일 임계값이 舊 모델 기준이라 새 모델에서 재검증되지 않았다 | 3구간 모델로 91일 백테스트 재실행, 가드레일 임계값 재조정 |
| 잠금·보상 쿠폰 중복 적용 | 가격 잠금 쿠폰과 오늘의 보상 쿠폰을 한 주문에 함께 쓰면 총혜택이 38%(또는 재정의될 원 단위 캡)를 넘을 수 있다 | Cafe24가 한 주문에 할인코드 1개만 허용함을 활용해 "더 큰 혜택 하나만 적용" 규칙을 서버·화면 양쪽에서 강제(FR-LOCK04) |

**추가 대응:** 데이터 오류·결측·비영업일 예외 상황을 출시 전 테스트 항목에 포함한다.

## 13. 비로그인 참여·쿠폰·알림 처리

우리 사이트에는 로그인 기능을 두지 않는다. 참여 기록 확인 방식은 두 안을 비교해 결정한다.

| 안 | 기록 확인 방법 | 고려할 점 |
| --- | --- | --- |
| 브라우저 익명번호 | 브라우저에 저장한 번호로 서버 기록 조회 | 입력 불필요. 다른 브라우저·데이터 삭제 후 확인 어려움 |
| 참여번호·확인 비밀번호 | 사용자가 입력한 정보로 서버 기록 조회 | 다른 기기에서 확인 가능. 분실·중복 입력·인증 처리 필요 |

**쿠폰:** 가격 잠금 차액 쿠폰과 오늘의 보상(안정형/공격형) 쿠폰 모두, 카페24에서 발급한 쿠폰 번호를 해당 참여 기록에 배정한다. 사용자는 우리 사이트에서 번호를 확인한 뒤 자사몰에서 로그인·등록해 사용한다. 한 주문에는 두 쿠폰 중 하나만 적용한다(8.5절 FR-LOCK04).

**가격 알림(FR-EV03):** 로그인이 없으므로 이메일 주소 기준으로 등록·발송하며, 참여번호 방식과 별도로 이메일 자체를 식별자로 사용한다. 수신 거부 처리, 이메일 유효성 검증, 발송 실패 처리 규칙은 출시 전 확정한다.

## 19. 검증 방법

- **기능 검증:** 수집 데이터·계산 결과·표시 가격을 비교하고, 연동 후 테스트몰의 실제 가격까지 대조한다.
- **사용성 검증:** 처음 보는 사용자가 오늘 가격 확인, 상품 선택, 구매 이동을 수행하는지 관찰한다.
- **운영 검증:** 다음 날 판정, 가격 동일·미갱신, 쿠폰 중복 요청·실패, 알림 오발송 상황을 확인한다.
- **효과 검증:** 재방문·상세 조회·구매 이동 기록을 확인하고, 인터뷰로 방문 이유를 보완한다. 단순 지표 상승만으로 가격 변동의 효과를 단정하지 않는다.

## 20. 출시 조건(Definition of Done)

1. Bread Market: 실제 API 수집 → 가격 계산 → 화면 표시 → 상품별 자사몰 이동이 동작한다.
2. 가격 연동: 합의한 범위에서 표시 가격과 자사몰 반영 가격을 대조한다.
3. 예측·보상: 참여 기록과 판정이 일치하고, 성공 기록에 정한 보상이 중복 없이 제공된다.
4. 알림: 등록·판정·발송·수신거부 흐름이 중복 발송 없이 동작한다.
5. 확장 설계: Bakery ETF·FX Bakery·Bread Index 3종의 필수 설계 항목을 작성한다.
6. 12장 세 가지 핵심 리스크(검색키워드 적합성·표시결제 불일치·법적 위험)에 대한 대응이 완료된다.
7. 인수인계: API 키 관리·배포 가이드·코드 구조·운영 방법을 전달한다.

## 23. 반영하지 않는 제안

- **매출 규모 추정:** 실제 판매량, 전환율, 객단가, 원가율이 없어 수치를 제시하지 않는다. 기업 데이터 확보 후 보수·기준·공격 시나리오로 별도 산출한다.
- **38%p 상한 초과 이벤트:** 가격 안전 원칙과 RFP 절대 상한 조건에 어긋나 채택하지 않는다. 추가 혜택은 38%p 안에서 재배분하거나 배송비·사은품 등 가격 외 혜택으로 검토한다.
- **빵 도감·씰 수집 콘텐츠:** [[makji-stock-prototype]] 전제에 따라 제외한다.
